# Принципиальные проектные решения (Практическая работа №8)

## Решение 1. Отказ от публичного setter статуса в пользу доменных методов конечного автомата
Поле `status` в классе `BusinessTrip` объявлено `private`, а метод `setStatus(TripStatus)` намеренно отсутствует. Все переходы между состояниями (`DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED`, `CANCELLED`, `COMPLETED`) выполняются исключительно через предметные методы `submit()`, `approve()`, `reject(String)`, `cancel()` и `complete(LocalDate)`. Каждый метод сначала проверяет допустимость исходного состояния (генерируя `IllegalStateException` при нарушении графа переходов), затем проверяет аргументы операции (`IllegalArgumentException`), и только при успехе меняет состояние объекта, сохраняя атомарность и неизменность объекта при ошибке.

## Решение 2. Централизация календарных инвариантов и правила варианта №6 в методе validateDates
Проверка корректности дат командировки (`start != null`, `end != null`, `!end.isBefore(start)`) и индивидуальное правило варианта №6 (дополнительная проверка даты с параметром `MAX_TRIP_DURATION_DAYS = 35L`: длительность командировки `ChronoUnit.DAYS.between(start, end) + 1` не должна превышать 35 календарных дней) инкапсулированы в приватном методе `BusinessTrip.validateDates(start, end)`, вызываемом в конструкторе. Благодаря этому ни один экземпляр `BusinessTrip` не может быть создан с некорректным интервалом дат.
