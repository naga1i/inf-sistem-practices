# Принципиальные проектные решения (Практическая работа №3-4)

## Решение 1. Централизация граничных констант и предварительная валидация до вычислений
Все пороговые значения предметной области (`MIN_QUANTITY = 1`, `MAX_QUANTITY = 10_000`, `MAX_UNIT_PRICE = 5_000_000.0`, `MAX_DISCOUNT_PERCENT = 30.0`, `VAT_RATE = 20.0`, а также порог бесплатной обработки заказа по варианту 6 `FREE_PROCESSING_THRESHOLD = 35_000.0`) вынесены в именованные константы класса `OrderCalculator`. Метод `validateInput(...)` проверяет все входные параметры (включая защиту от `NaN` и `Infinite`) до выполнения любых арифметических операций. Это предотвращает расчёт по некорректным данным и позволяет при изменении бизнес-правила менять порог ровно в одном месте кода.

## Решение 2. Декомпозиция расчёта без дублирования формул и учёт ограничений типа double
Логика расчёта разделена на чистые атомарные методы `calculateBase`, `applyDiscount`, `calculateVat`, а итоговый метод `calculateTotal` последовательно вызывает их без дублирования арифметических выражений. Для количества выбран целочисленный тип `int` (так как штуки неделимы и диапазон 1..10 000 укладывается в `int`), а для денежных сумм и процентов в рамках учебного контракта использован `double` с форматированием до двух знаков (`%.2f`). При этом в промышленной финансовой разработке вместо `double` (имеющего двоичное представление IEEE 754 и погрешности вроде `0.1 + 0.2 != 0.3`) следует применять `BigDecimal` с явным режимом округления `RoundingMode.HALF_UP`.
